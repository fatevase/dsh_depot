# DSH 离线插件管理器

在当前 DSH 中查看后来安装的第三方插件，并载入和导出离线包。从 DSH 左侧栏的“离线插件”进入；侧栏收起时保留图标入口。页面沿用官方插件页的列表布局，跟随 DSH 的浅色、深色或跟随系统设置，点击插件可查看详情。

## 载入离线插件

1. 点击右上角“载入插件”。
2. 拖入 `.tgz` 离线包或已经构建、包含运行依赖的成品文件夹，也可点击选择文件。
3. 等待准备完成，核对插件名称、版本、平台和检查提示。此时尚未安装。
4. 点击一次“确定”，通过当前 DSH 自带的包管理服务安装并启用插件。不会下载依赖或执行安装脚本。
5. 根据实际结果重新加载或重启 DSH。可关闭窗口，已开始的任务会继续，在“操作记录”查看结果。

未通过检查的包会显示原因并阻止载入。同名插件会被替换；卸载保留配置和业务数据。官方插件和宿主内置组件不在此页面显示；插件启停与配置继续使用 DSH 官方管理器。

首次安装管理器需要已有的 DSH。完整安装包附带用于运行安装助手的 Node，轻量包需要 Node `^22.19.0 || >=24.0.0`。每次离线操作均信任现有锁定结果，不以另一份已安装快照是否存在或一致作为条件；避免因缺少仓库复审元数据而失败。不重新审核这些旧依赖的发布时间与信任级别策略，归档完整性检查和禁止安装脚本仍保留，不修改全局配置。实际缺少依赖时会保留错误并停止，不联网下载、不伪造缓存。pnpm 12 已覆盖仓库元数据缓存全空的场景；旧版 pnpm 11 的 hoisted 布局仍需要原有的常规解析缓存，本策略免去的是供应链复审元数据，不能补出缺失的依赖或旧版解析缓存。安装助手使用目标 DSH 的 CLI（外部脚本）或公开包管理服务（应用内）、宿主运行时及自带 pnpm；新版官方 Desktop 的外部 CLI 要求退出应用后执行，应用内载入则使用正在运行的 DSH 服务。

“等待加载”表示文件操作已完成；只有宿主观察到相应插件实际加载后才显示“已加载”。安装不遍历或备份整个已安装依赖目录，失败时保留真实错误与日志，不自动回滚。可修正后重装成品或先前版本；旧版完整恢复点仍可从外部脚本恢复。当前适配 DSH `0.2.1-rc.2 / 0.2.1-rc.3`，实际平台验证结果以随包报告为准。

## 把已安装插件带到另一台机器

1. 在联网机器先按 DSH 的正常方式安装插件，并确认插件能够运行。
2. 打开“离线插件”，找到所需插件，点击进入详情，再点击“导出插件”。不需要退出 DSH。
3. 在插件详情的“导出与迁移”中查看进度。完成后下载 `.tgz`，同时保存显示的 SHA-256；下载保留 24 小时。
4. 把文件带到相同系统、架构及兼容 DSH 的目标机器，点击“载入插件”，拖入文件，查看提示后点击“确定”，再按提示重新加载或重启 DSH。
5. 在目标机另行配置账号和外部服务，检查插件入口与实际功能。

导出范围是当前插件程序和声明的运行依赖；不读取 DSH 配置、登录状态、聊天记录或 profile 数据。包内的 `.env`、`.env.*`、`.npmrc`、Git、日志和缓存会排除，清单可在结果中查看。无法识别被直接写入任意 JS/JSON 程序的私有值；分发自定义程序前请自行确认。

导出不会下载、编译或运行安装脚本，也不会修改源插件。管理器自身可导出，内置 DSH 核心由目标宿主提供。原生模块按源平台、运行时类型、Node ABI 和 Linux libc 保守限制。系统命令、Python 环境、浏览器、驱动和模型需另行准备。导出成功表示归档检查通过，不能替代目标机器的实际启动验证。

遇到 `MISSING_DEPENDENCY` 请在源环境修复插件；`PEER_UNCONFIRMED` 表示无法确认共享依赖；`DEPENDENCY_CYCLE_UNSUPPORTED` 表示首版暂不支持该依赖环。`SOURCE_CHANGED` 表示导出期间程序发生变化，等待更新完成后重试。取消或失败不会移除源插件；进程退出时未完成导出标记失败，重新导出即可。
