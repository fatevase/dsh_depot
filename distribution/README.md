# 插件分发流水线

按人工维护的构建配置，重复执行以下流程：

1. 检查已收录仓库的新版本，将新发现插件加入候选清单。
2. 比较宿主兼容性、源码、构建配置、依赖锁与目标平台，无变化时跳过。
3. 在对应系统构建，打包完整运行依赖。
4. 使用原版 DSH，在空缓存和网络隔离下验证安装、启动与插件加载。
5. 发布安装包、校验和与报告，更新公开目录。

普通插件的构建配置位于 `recipes/`。`manager/` 仅保留配套管理器的 CI 验证和发布编排，管理器源码位于 [plugins/dsh-depot-manager](../plugins/dsh-depot-manager/)，网站位于 [web](../web/)。

操作步骤见[分发维护说明](MAINTAINING.md)，工作区安装、模块命令和独立工作流见[根维护说明](../MAINTAINING.md)。

## 版本维护规则

当前只维护一条最新版本线。DSH 跟随 npm 官方 `latest`（包括官方指定的 RC），插件优先选择同包名的最新正式 Release，其次为版本标签；没有匹配发布版时使用默认分支。构建前把提交、宿主和依赖锁固定下来。新版本不兼容、源码无法获取或构建配置失效时显示阻塞原因，不用旧版本代替当前版本。

`Refresh latest DSH and plugins` 每 6 小时刷新已适配插件的输入，测试通过后提交版本与依赖锁，再触发三平台构建。普通分发每批最多 5 个插件 / 15 个平台任务。99 个候选每小时检查一次，每轮最多处理 5 个有变化的仓库；不变的成功或失败输入不重复消耗编译时间，手动运行可指定批次重试。候选试编译仍不等于完成离线验证，不会直接混入正式下载目录。

网站只展示当前源码和当前 DSH 基线的包。GitHub 的历史 Release 保留原链接作为记录，不为旧版继续重建，也不会复制构建产物进入 Git 源码仓库。
